================================================================================
SECTION 1 - UNDERSTANDING THE APPLICATION
================================================================================

1.1 PURPOSE
--------------------------------------------------------------------------------
A personal and small-team attendance / timesheet system. Employees clock in and
out, or enter days by hand; the app computes hours worked against a configurable
daily target, tracks punctuality (late arrivals / early departures), annual leave
balance, and produces printable signed timesheet reports. Admins can view and
edit any employee's record, manage roles, and run org-wide actions.

1.2 TARGET USERS
--------------------------------------------------------------------------------
  * Employee ("user" role)  - logs their own attendance, views their own stats.
  * Administrator ("admin") - everything an employee can do, plus: view/edit any
    employee's data, edit ANY employee's schedule settings (employees cannot
    edit their own - see H-4), grant/revoke admin, bulk-apply holidays, view
    system stats, manage accounts, read the audit log, set org-wide settings.

Design context strongly suggests a Gulf/Saudi deployment: the default working
week is Sunday-Thursday, and there is first-class Ramadan seasonal-hours support
capped at the 6-hour statutory day.

1.3 ARCHITECTURE
--------------------------------------------------------------------------------
FRONTEND
  Single static file, index.html: 1,173 lines of CSS + ~900 lines of markup +
  ~3,800 lines of JavaScript, all inline. No build step, no framework, no
  bundler, no dependency manifest. All app code lives in one IIFE using ES5
  style (var, function expressions) with async/await layered on top.
  ONE runtime dependency, loaded at page load:
      import { createClient } from "https://esm.sh/@supabase/supabase-js@2"
  There is no local copy, no version pin below the major, and no integrity hash.

BACKEND
  Supabase (Postgres 17.6). No custom server, no edge functions. The browser
  talks directly to PostgREST and GoTrue. Authorisation is entirely Row Level
  Security plus five SECURITY DEFINER RPCs.

  Tables (public schema, RLS enabled on all 5):
    profiles      (8 rows)   id -> auth.users, email, full_name, role, created_at
    entries       (345 rows) id, user_id, date, clock_in TEXT, clock_out TEXT,
                             type TEXT, note TEXT, created_at, updated_at
                             UNIQUE (user_id, date)
    user_settings (6 rows)   user_id PK, settings JSONB, updated_at
    audit_log     (46 rows)  actor, action, table, record, target, values, ts
    app_settings  (1 row)    singleton: announcement, announcement_active,
                             allow_registration, default_settings

  Functions: is_admin(), handle_new_user(), log_entry_change(),
    log_profile_change(), set_updated_at(), admin_db_stats(),
    admin_list_users(), admin_set_user_active(), admin_delete_user(),
    admin_audit_log().

  Triggers: entries_audit (AFTER I/U/D), entries_set_updated_at (BEFORE U),
    profiles_audit (AFTER I/U), settings_set_updated_at (BEFORE U),
    auth.users on_auth_user_created (AFTER I).

  RLS summary:
    profiles      SELECT/UPDATE: id = auth.uid() OR is_admin()   <-- see C-1
    entries       SELECT/INSERT/UPDATE/DELETE: user_id = auth.uid() OR is_admin()
    user_settings SELECT: own or admin.  INSERT/UPDATE: is_admin() ONLY.
    audit_log     SELECT: is_admin(). No INSERT/UPDATE/DELETE policy (writes
                  only via SECURITY DEFINER triggers) - correctly immutable.
    app_settings  SELECT: auth.uid() IS NOT NULL.  UPDATE: is_admin().

AUTH / SESSION
  Supabase email+password. Sessions (access + refresh JWT) are held in
  localStorage by the Supabase client - the default. Sign-in state is driven
  entirely by supabase.auth.onAuthStateChange (see H-2).
  Password minimum is 6 characters and leaked-password protection is DISABLED
  on the project.

PWA
  manifest.json + sw.js. The service worker is network-first with a cache
  fallback, and caches only ./index.html, ./manifest.json and two icons.

1.4 PAGES / COMPONENTS
--------------------------------------------------------------------------------
There is one page. Views are toggled by class:
  #authScreen  - sign in / register / forgot password
  #appShell    - header (schedule line, viewer switcher, user chip, overflow
                 menu, "Today" seal), 5 banners (announcement, viewing-other,
                 open-shift reminder, backup reminder), hero card (Monthly Avg),
                 4 stat cards, Schedule Settings card, Team & Access card,
                 New Entry card (quick clock + manual form), and a tabbed
                 content card: Log | Trends (Weekly/Monthly/Yearly) | Calendar |
                 On Time | Team (admin) | Admin (admin).
                 Plus a footer (export/import/clear), a fixed mobile bottom nav,
                 and a sticky clock bar (which never renders - see H-6).

1.5 MAJOR USER JOURNEYS MAPPED
--------------------------------------------------------------------------------
  J1  First run: register -> auto sign-in -> empty log with a first-run empty
      state -> Clock In Now -> Clock Out Now -> stats populate.
  J2  Daily returning user: open -> Clock In (quick clock or bottom-nav button)
      -> later Clock Out -> "Today" seal updates.
  J3  Correcting a day: Log tab -> Edit -> change times -> Save Changes.
  J4  Planned leave: New Entry -> From/To range -> type Annual Leave -> Apply.
  J5  Reviewing: Trends (Weekly/Monthly/Yearly), Calendar, On Time.
  J6  Reporting: filter to a month -> Print Report -> sign.
  J7  Backup/restore: Export JSON/CSV -> Import JSON/CSV.
  J8  Admin - configure an employee: viewer switcher -> Schedule Settings ->
      save (or "Apply to everyone").
  J9  Admin - org holiday: Team & Access -> Apply to Everyone.
  J10 Admin - roles: Team & Access -> Employee/Admin toggle.
  J11 Admin - operations: Admin tab -> stats, users, activity log, app settings.

FEATURE DEPENDENCIES
  settings.workDays / targetMin / periods  ->  isScheduled(), scheduleFor(),
  computeEntry()  ->  every stat card, chart, table, calendar colour, print
  report, punctuality figure and leave balance. A wrong or missing settings row
  silently corrupts EVERY number in the app (see H-4).

1.6 STATED ASSUMPTIONS (inferred, not documented anywhere in the repo)
--------------------------------------------------------------------------------
  A1  Only "Regular" days count toward averages and the overtime bank. This is
      an explicit code comment - but it is invisible to users and produces the
      wrong headline number for WFH-heavy teams (C-4).
  A2  Weeks start on Sunday. Hardcoded; not derived from workDays.
  A3  Clock times are wall-clock local, timezone-naive, stored as TEXT.
  A4  A clock-out earlier than the clock-in means an overnight shift (H-5).
  A5  Schedule settings are an ADMIN-OWNED concept, not a user preference (H-4).
  A6  Every user in the org shares one app_settings row.
  A7  There is exactly one org / tenant. There is no tenancy boundary at all -
      every admin sees every user in the whole database.
  A8  The device clock is trusted absolutely for all punches (M-14).


================================================================================
SECTION 2 - EXECUTIVE SUMMARY
================================================================================

Attendance Ledger is a genuinely well-crafted piece of front-end work. The
visual design is coherent and distinctive, the dark mode is properly thought
through (elevation via surface colour rather than shadow), the mobile
card-table pattern is thoughtful, the modal focus trap is correctly implemented
including the Shift+Tab and "focus escaped" cases, double-tap on the clock is
guarded by a real in-flight flag rather than just a disabled attribute, and the
code comments are unusually honest about why decisions were made. There is a
real regression test suite. This is far above the norm for a solo project.

That quality makes the actual risk profile more surprising, because the
problems are concentrated in the places the polish does not reach: the
authorisation model, the aggregate arithmetic, and the failure paths.

THE FIVE THINGS THAT MATTER

1.  ANY SIGNED-IN EMPLOYEE CAN MAKE THEMSELVES AN ADMINISTRATOR.
    This is not theoretical. It was executed against the live database and
    rolled back. The RLS UPDATE policy on `profiles` omits WITH CHECK, so
    Postgres reuses the USING clause - which is satisfied both before and after
    the change. One HTTP PATCH promotes the caller to admin, after which they
    can read and edit every employee's attendance, delete accounts, and read
    the audit log. Every other access control in the product is downstream of
    this, so every other control is currently decorative. This alone should
    block any further rollout.

2.  THE HEADLINE NUMBERS DO NOT ADD UP.
    A week containing two 8h days, one forgotten clock-out and one blank
    imported row renders a card reading Total 16h, Target 32h, Overtime/Under
    0h. Reproduced against the shipped summarize(). A fully missed workday
    moves the Overtime Bank by exactly zero. Three 9-hour work-from-home days
    summarise to an average of "0h". For a timesheet product - a product whose
    entire value is the accuracy of a number a manager signs - this is the most
    damaging class of defect there is, because it is silent and plausible.

3.  THE APP DIES SILENTLY IF ONE THIRD-PARTY CDN IS UNREACHABLE.
    The entire application is one ES module whose first line imports from
    esm.sh. If that request fails - CDN outage, corporate proxy, captive
    portal, or simply an installed PWA opened offline - the module never
    executes. The user is shown a pixel-perfect sign-in form in which nothing
    is wired up. Typing a password and pressing Sign In does nothing at all.
    No spinner, no error, no explanation. Verified in a browser with the CDN
    blocked. The same import is also an unpinned, unhashed supply-chain
    dependency with full access to the auth tokens in localStorage.

4.  AN ADMIN EDITING SOMEONE ELSE'S RECORD IS NEVER WARNED.
    The banner written for exactly this purpose - "Edits here save to their
    record, not yours" - carries an inline style="display:none" that outranks
    the .show class the JavaScript toggles. It has never rendered. Verified by
    measuring computed style. Meanwhile "Apply to Everyone" overwrites every
    existing entry across a date range for every user, blanking real clock
    times, with no undo and no per-day preview.

5.  ACCESSIBILITY IS BELOW THE LEGAL FLOOR IN SEVERAL PLACES.
    Secondary text sits at 2.06:1 to 3.06:1 contrast against its background
    where WCAG AA requires 4.5:1 - measured, not estimated, across six
    different classes. The tab widget exposes no role, no aria-selected and no
    tablist. On mobile every data table is converted to display:block, which
    removes the table semantics entirely and leaves column names only in CSS
    ::before content, which assistive technology does not announce. A screen
    reader user on a phone hears an undifferentiated stream of numbers.

WHAT IS GENUINELY GOOD
    Modal focus management; the punch double-tap lock; the audit log design
    (append-only, no UPDATE/DELETE policy, SECURITY DEFINER triggers, logging
    before cascade delete); last-admin and self-deletion safeguards inside the
    admin RPCs; the CSV parser (quotes, escaped quotes, embedded newlines, BOM,
    CRLF, ambiguous D/M vs M/D resolved once with a user prompt); the deliberate
    dark-mode token system; reduced-motion support; the safety caps on bulk
    operations; and a regression suite that extracts live code rather than
    reimplementing it.

RECOMMENDED POSTURE
    Do not onboard additional employees until C-1 is fixed. C-1 is a
    ten-minute database change. C-2 and C-3 are each under an hour. C-4 is a
    focused change to one function plus a product decision. The four criticals
    together are realistically a single day of work, and they move this from
    "not deployable" to "deployable with known gaps".

SEVERITY COUNTS
    Critical  4  |  High 14  |  Medium 24  |  Low 17  |  Potential risks 6

SECTION 3 - CRITICAL ISSUES (P0)
================================================================================

--------------------------------------------------------------------------------
C-1  ANY AUTHENTICATED USER CAN PROMOTE THEMSELVES TO ADMINISTRATOR
--------------------------------------------------------------------------------
Issue:
  The RLS policy `profiles_update_own_or_admin` is defined with USING
  ((id = auth.uid()) OR is_admin()) and NO WITH CHECK clause. PostgreSQL
  documents that when WITH CHECK is omitted from an UPDATE policy, the USING
  expression is used for the row being written as well. The predicate is
  `id = auth.uid()`, which is true for the user's own row both before and after
  the update - so the policy permits the user to change ANY column of their own
  profile, including `role`.
  The `authenticated` role additionally holds a column-level UPDATE grant on
  profiles.role, and no BEFORE UPDATE trigger on profiles rejects role changes
  (profiles_audit is AFTER, and only logs).
  The only guard that exists is client-side: the Employee/Admin toggle is
  rendered inside an admin-only card. That guard is bypassed by sending the
  request directly.

Severity: Critical
Category: Security - Broken Access Control / Privilege Escalation (OWASP A01)
Location:
  Database: policy `profiles_update_own_or_admin` on public.profiles
  Grants:   authenticated has UPDATE on public.profiles(role)
  Client:   index.html:5270 (the legitimate role-change call, for reference)

Steps to Reproduce (CONFIRMED - executed live, then rolled back):
  1. Sign in as any ordinary employee.
  2. Read the access token from localStorage (or just use the app's own client).
  3. Send:
        PATCH /rest/v1/profiles?id=eq.<your own uuid>
        Authorization: Bearer <your access token>
        apikey: <the anon key that is already in the page source>
        Content-Type: application/json
        {"role":"admin"}
  4. Reload the app.

  Executed on the live project as a DO block that impersonated an existing
  ordinary user via request.jwt.claims, performed the UPDATE, and then raised
  an exception to abort the transaction. Result:
        NOTICE: role after self-update = admin, is_admin() now returns t
        ERROR:  AUDIT_ROLLBACK role=admin is_admin=t   (transaction aborted)
  Post-check confirmed no persistent change: 1 admin, 7 users - identical to
  the pre-check.

Expected Behavior:
  A user may update their own full_name. Only an existing admin may change any
  profile's `role`, and nobody may change `id` or `email` (email is owned by
  auth.users).

Actual Behavior:
  A user may rewrite every column of their own profile row, including `role`,
  and is_admin() returns true on the very next statement.

Risk / Impact:
  Total collapse of the authorisation model. A promoted user can:
    - read and edit every employee's attendance (entries RLS is `OR is_admin()`)
    - read every employee's settings
    - read the full audit log, including who changed what and when
    - grant and revoke admin on anyone
    - deactivate accounts and PERMANENTLY DELETE users together with every
      entry they ever logged (admin_delete_user cascades auth.users)
    - overwrite the whole team's schedule settings and attendance
  In an HR context this is also a privacy incident: attendance and sick-leave
  records for every employee become readable by any employee.
  Note the escalation IS recorded in audit_log as a role_change, so it is
  detectable after the fact - but nothing prevents it, and a promoted attacker
  cannot delete audit rows (no DELETE policy exists), which is the one piece of
  good news here.

Recommended Fix:
  Immediate (database, no app change required):

    -- 1. Stop the API from touching the privileged columns at all.
    REVOKE UPDATE ON public.profiles FROM authenticated, anon;
    GRANT  UPDATE (full_name) ON public.profiles TO authenticated;

    -- 2. Make the policy explicit rather than relying on the implicit reuse.
    DROP POLICY profiles_update_own_or_admin ON public.profiles;
    CREATE POLICY profiles_update_own ON public.profiles
      FOR UPDATE TO authenticated
      USING (id = (select auth.uid()))
      WITH CHECK (id = (select auth.uid()));

    -- 3. Belt and braces: reject any role change that did not come through
    --    the sanctioned RPC.
    CREATE OR REPLACE FUNCTION public.guard_profile_role()
    RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
    BEGIN
      IF NEW.role IS DISTINCT FROM OLD.role AND NOT public.is_admin() THEN
        RAISE EXCEPTION 'Only an administrator can change a role';
      END IF;
      NEW.id    := OLD.id;      -- immutable
      NEW.email := OLD.email;   -- owned by auth.users
      RETURN NEW;
    END $$;
    CREATE TRIGGER profiles_guard_role BEFORE UPDATE ON public.profiles
      FOR EACH ROW EXECUTE FUNCTION public.guard_profile_role();

  Then move the role change itself to a SECURITY DEFINER RPC
  (admin_set_user_role) that re-checks is_admin() and enforces the
  "last admin" rule server-side, exactly as admin_set_user_active already does.
  Today that last-admin rule (index.html:5248-5254) exists ONLY in the browser,
  so even a legitimate admin can strip the final admin by calling the API
  directly and permanently lock the organisation out of its own admin panel.

  AUDIT ACTION: before deploying, review audit_log for any historical
  `role_change` row whose actor_id equals its target_user_id and whose
  new_values.role = 'admin'. That is the signature of this being exploited.

Priority: P0

C-2  THE APPLICATION FAILS COMPLETELY AND SILENTLY IF esm.sh IS UNREACHABLE
--------------------------------------------------------------------------------
Issue:
  The whole application is one `<script type="module">` whose first statement
  is a remote import. If that fetch fails for any reason, the module body never
  executes, so not one event listener is attached. Because the sign-in screen is
  the default-visible markup and needs no JavaScript to render, the user is
  presented with a complete, correct-looking, entirely inert application.

Severity: Critical
Category: Bug / Reliability / Architecture / Supply chain
Location: index.html:2099
          `import { createClient } from "https://esm.sh/@supabase/supabase-js@2"`
          sw.js:14-19 (SHELL_FILES does not and cannot include the CDN module)

Steps to Reproduce (CONFIRMED in headless Chromium):
  1. Serve the app over http and block all requests to esm.sh.
  2. Load index.html. The sign-in card renders perfectly.
  3. Fill in email and password, click Sign In.
  Measured result: button text remains "Sign In", the config-warning panel
  stays display:none, zero page errors surface to the user, and the form
  submit does nothing. The page is indistinguishable from a working one.

  Real-world triggers: esm.sh outage or rate-limit; corporate proxy or firewall
  blocking unknown CDNs; hotel/airport captive portal; an ad/tracker blocker
  with a broad CDN rule; a country-level block; OR - most likely of all - the
  installed PWA being opened with no connectivity. The service worker faithfully
  serves index.html from cache, and then the app cannot boot.

Expected Behavior:
  Either the dependency is local so this cannot happen, or the failure is caught
  and the user is told: "Can't reach the server. Check your connection and
  reload."

Actual Behavior:
  A fully rendered, completely non-functional application with no feedback of
  any kind. Users will conclude their password is wrong.

Risk / Impact:
  Total loss of availability from a dependency the team does not control. The
  product is marketed as an installable PWA (manifest, icons, service worker,
  standalone display) which sets an explicit offline expectation it cannot meet.
  Employees who cannot clock in lose their record for that day.

  There is a second, more serious dimension. The import is pinned only to the
  MAJOR version (`@2`), served from a third party, with no Subresource
  Integrity hash. Whatever esm.sh returns tomorrow executes with full access to
  the page - including the Supabase access and refresh tokens in localStorage
  and every attendance record on screen. A compromise of that CDN, or of any
  supabase-js 2.x release, is a silent full compromise of this application.

Recommended Fix:
  1. Vendor the dependency. Download a specific version of the ESM build, commit
     it as ./vendor/supabase-js-2.x.y.js, and import it relatively. This removes
     the outage, the proxy problem, the offline problem and the supply-chain
     problem in one change, and costs ~120KB in the repo.
  2. Add it to sw.js SHELL_FILES so the PWA can genuinely boot offline.
  3. Regardless, wrap boot in a visible failure path:
         <script type="module">
           import("./vendor/supabase-js.js")
             .then(m => start(m.createClient))
             .catch(() => document.getElementById("authConfigWarning")
               .replaceChildren("Couldn't load the app. Check your connection
                                 and reload."),
               document.getElementById("authConfigWarning").style.display="block");
         </script>
  4. If the CDN must be kept, pin the exact version and add an integrity hash.
  5. Separately: even with the code loaded, the app has no offline data layer.
     Be explicit in the UI that it needs a connection, or implement an outbox
     that queues punches locally and replays them.

Priority: P0

--------------------------------------------------------------------------------
C-3  "APPLY TO EVERYONE" IRREVERSIBLY DESTROYS REAL CLOCK-IN/OUT DATA
--------------------------------------------------------------------------------
Issue:
  The Team & Access -> "Apply to Everyone" action writes a payload of
  {clockIn:"", clockOut:"", type, note} to EVERY calendar day in the chosen
  range for EVERY registered user, updating existing rows in place. Any day in
  that range on which an employee had actually recorded hours has its clock_in
  and clock_out overwritten with null. There is no undo, no preview of what
  will be overwritten, and no exclusion of days that already contain worked
  hours.

Severity: Critical
Category: Data loss / Business logic
Location: index.html:5287-5377 (bulkApplyBtn handler); payload built at :5357

Steps to Reproduce:
  1. Sign in as admin. Confirm an employee has real hours logged on, say,
     10 August (08:00-16:30).
  2. Team & Access -> Apply to Everyone -> From 09 Aug, To 15 Aug,
     Day Type "Public Holiday", note "National Day".
  3. Confirm the dialog.
  4. Switch the viewer to that employee and open 10 August.

Expected Behavior:
  Either days that already contain recorded hours are skipped and reported
  ("3 days skipped - hours already recorded"), or the confirmation names them
  explicitly and offers a choice.

Actual Behavior:
  The real 08:00-16:30 punch is gone. The row now reads Public Holiday with no
  times. The employee's monthly total silently drops by a day's work.
  The confirmation text does say "replacing any existing entries on those
  dates", but it gives no count, no list, and no indication that recorded
  working hours - as opposed to placeholder rows - are among them.

Risk / Impact:
  Permanent, unrecoverable loss of payroll-relevant data across the entire
  organisation from a single click. The audit_log DOES capture old_values for
  every overwritten row, so recovery is technically possible, but only by hand
  through SQL - there is no restore path in the product, and nothing tells the
  admin that anything was lost.
  The blast radius is large by design: up to 500 entries (dates x team members)
  in one action.

Recommended Fix:
  1. Before writing, fetch the affected rows (the code already does exactly this
     at :5344 to find IDs) and partition them: rows with a clock_in or clock_out
     are "occupied".
  2. Name the damage in the confirmation:
       "12 of these 35 entries already contain recorded hours. Overwriting them
        cannot be undone."
     with a default of SKIP and an explicit opt-in to overwrite.
  3. Skip non-working days for that user unless the type is a public holiday
     (see B-4 - marking a weekend as Annual Leave also burns leave entitlement).
  4. Longer term, add a soft-delete / restore-from-audit path so any bulk action
     is reversible for 30 days.

Priority: P0

--------------------------------------------------------------------------------
C-4  AGGREGATE HOURS ARITHMETIC IS INTERNALLY INCONSISTENT AND HIDES SHORTFALLS
--------------------------------------------------------------------------------
Issue:
  summarize() (index.html:2632-2666) adds a Regular day's target to targetSum
  unconditionally, but adds to workedSum and diffSum only when the day actually
  has hours. A Regular day that is open (clocked in, never out) or blank
  (created by an import or a range apply) therefore inflates Target while
  contributing nothing to Total and nothing to Diff. The three figures are
  printed side by side on the same card, so they visibly fail to reconcile.

  Compounding this, every non-"regular" day type - WFH, Business Trip,
  Training, Half Day Leave - is excluded from workedSum, targetSum, diffSum and
  loggedDays entirely, while its own Log row still displays a worked figure, a
  target and a Diff pill.

Severity: Critical
Category: Business Logic / Data correctness
Location: index.html:2632-2666 (summarize)
          Consumers: renderStats (hero Monthly Avg, Week Avg, Overtime Bank),
          renderWeekly, renderMonthly, renderYearly, buildPrintReport, Team tab.

Steps to Reproduce (CONFIRMED - shipped summarize() executed directly):

  (a) Reconciliation failure
      Week: Sun 08:00-16:00, Mon 08:00-16:00, Tue clocked in at 08:00 and never
      out, Wed a blank Regular row.
      MEASURED card output: Total=16h  Target=32h  Overtime/Under=0h
      16h - 32h = -16h, not 0h.

  (b) A whole missed workday is invisible
      One 8h day               -> Overtime Bank = 0h
      Same day + one unlogged Regular workday -> Overtime Bank = 0h
      MEASURED: identical. An 8-hour shortfall does not move the headline
      figure at all.

  (c) A fully worked month can report a zero average
      Three 9-hour days typed as WFH / Business Trip / Training:
      MEASURED: loggedDays=0, total=0h, avg=0h.
      The hero card reads "This Month's Average: 0h" and the progress bar
      reads "No regular workdays logged yet this month".

  (d) Row maths and card maths disagree
      A Half Day Leave 08:00-12:00:
      MEASURED Log row: Target 4h, Worked 4h, Diff 0h.
      MEASURED summarize() contribution: targetSum=0, diffSum=0.

Expected Behavior:
  Total - Target = Diff, always. A day the employee did not work should reduce
  the overtime bank. Days spent working - from home, on a trip, in training -
  should count as worked days. Whatever the rule is, the UI should state it
  where the number appears.

Actual Behavior:
  As measured above. The numbers are plausible, internally contradictory, and
  systematically flattering: shortfalls disappear and remote work vanishes.

Risk / Impact:
  This is the product's core output. These figures are printed onto a report
  with employee and manager signature lines - a document that may be used for
  payroll, overtime claims or performance conversations. Wrong numbers here are
  worse than a crash, because nobody notices. A remote-first employee appears
  to have worked zero hours. An employee who forgot to clock out on Friday
  appears to owe nothing.

Recommended Fix:
  1. Make summarize() self-consistent. Only add a day's target when that day
     also contributes worked time and a diff; or (better) treat an
     open/blank Regular workday as a genuine shortfall - workedMin 0, full
     target, negative diff - and surface it distinctly:
        "3 days incomplete - not counted"

     weekly card and five SVG charts - including tabs that are not visible.

     Severity: Medium  Category: Performance  Priority: P2

     background tabs

     (updating a hidden element) and continues while the tab is hidden.
     Location: index.html:5873-5875

     Fix: gate on document.visibilityState and on sign-in state; use

     Severity: Medium  Category: Performance  Priority: P2

M-22 Password policy is weak and leaked-password protection is off
     Minimum length is 6 characters (index.html:5131 and the HTML minlength).
     The Supabase security advisor reports leaked-password protection disabled.
     Impact: given C-1, a weak password on ANY employee account is a full

     Supabase dashboard, and consider requiring MFA for admins.
     Severity: Medium  Category: Security  Priority: P2

M-23 No security headers and no Content-Security-Policy
     GitHub Pages serves no CSP, no X-Frame-Options / frame-ancestors, no
     Referrer-Policy, no Permissions-Policy. The page is framable, so an admin
     could be clickjacked into "Delete Permanently".
     Fix: add <meta http-equiv="Content-Security-Policy"> with a strict
     default-src, script-src 'self', and connect-src limited to the Supabase
     origin. This also materially reduces the M-4 XSS impact. Note that a
     meta-tag CSP cannot set frame-ancestors - if clickjacking matters, host
     behind something that can send real headers.
     Severity: Medium  Category: Security  Priority: P2

M-24 SECURITY DEFINER trigger functions are exposed as public RPC endpoints
     The Supabase advisor flags that handle_new_user(), log_entry_change(),
     log_profile_change() and is_admin() are callable via /rest/v1/rpc/... by
     the `anon` role. They are trigger functions and will error rather than do
     damage, but they should not be in the exposed API surface at all.
     set_updated_at() additionally has a mutable search_path.
     Fix: REVOKE EXECUTE ON FUNCTION ... FROM anon, authenticated for the four
     internal functions (triggers run as the definer and are unaffected), and
     add SET search_path = public to set_updated_at().
     Severity: Medium  Category: Security hardening  Priority: P2

SECTION 7 - UX / UI ISSUES
================================================================================

UX-1  There is no onboarding. A first-time user lands on a dense dashboard with
      a hero card reading 0h, four zeroed stat cards, and no explanation of what
      Overtime Bank, Leave Balance or the "Today" seal mean. The first-run empty
      state in the Log is well done and is the only guidance present - it is
      below the fold on a phone. Recommend a 3-step first-run overlay: confirm
      your schedule (see H-4), clock in, see your first day.

UX-2  "Overtime Bank" is undefined terminology. It is signed monthly diff versus
      target, but nothing says so, it excludes non-Regular days (C-4), and its
      subtitle just repeats the month name. Users will read it as accrued
      bankable overtime, which it is not.

UX-3  Two different mental models for schedules. "Standard Start/End" plus
      "Target Hours" can disagree (08:00-16:00 is 8h; set target to 7h and the
      app happily flags you as leaving early while telling you that you met
      target). Nothing reconciles or warns about the mismatch.

UX-4  The Settings gear is buried in a three-dot overflow menu, and it is the
      only route to the single most important configuration in the product.
      For non-admins it is absent entirely with no explanation (H-4).

UX-5  Settings and Team & Access open as inline cards near the top of the page
      rather than as a modal or route. On a phone the user is scrolled into a
      long form with the rest of the app still below it, and "Close" is at the
      bottom. There is also no unsaved-changes guard - closing discards silently
      (the code comments acknowledge this is intentional; it still surprises).

UX-6  No undo anywhere. Delete entry, bulk delete, Clear All, Apply to Everyone
      and Delete User are all immediate and permanent. Confirmation dialogs are
      good (Clear All is correctly two-step, danger dialogs correctly default
      focus to Cancel), but confirmation is not the same as recoverability.

UX-7  Success feedback is inconsistent. Some actions show a toast, some write to
      the qc-note, some just re-render silently. Saving the entry form, for
      instance, produces no confirmation at all - the form resets and the row
      appears, which is inferable but not stated.

UX-8  Error messages leak raw backend text. Repeated pattern:
      showToast("Couldn't save that entry: " + (err.message || err)). Users see
      PostgREST strings such as 'new row violates row-level security policy for
      table "entries"'. Map known codes to human sentences; the 23505 duplicate
      case is already handled well and shows what good looks like.

UX-9  Print Report silently uses whatever the Log filters happen to be. There is
      no preview and no statement of the covered period before the browser
      dialog opens. Combined with H-12's stale #printArea this is easy to get
      wrong on a signed document.

UX-10 The viewer switcher is a bare <select> in the header with the label
      "Viewing". For an admin it is the single most consequential control in the
      app - it decides whose record every subsequent action writes to - and it
      has the visual weight of a filter. With H-1 unfixed there is no banner
      either.

UX-11 The Team roster is not sortable, filterable or searchable, shows only the
      current month, and displays no target or overtime (the code comments
      explain why). For a manager this is the primary screen and it cannot
      answer "who is under target this month?".

UX-12 "Apply to everyone" appears twice with different meanings - a checkbox in
      Schedule Settings (overwrite everyone's schedule) and a button in Team &
      Access (write an entry for everyone). Both are irreversible bulk actions
      with similar names in adjacent cards.

UX-13 The seal shrinks its text below 12px for anything over 6 characters
      ("Clocked in", "Not logged", "Public Holiday"). Combined with the
      low-contrast palette this is the hardest-to-read element on the page.

UX-14 Charts have no empty-state guidance beyond "Nothing to chart yet." and no
      axis labels or gridlines - only a dashed target line explained in a legend
      below.

UX-15 The Trends tab merges three sub-views with three different filter bars
      that swap in and out as you switch sub-tabs. Filter state is not shared,
      so moving Weekly -> Monthly -> Weekly can land you on a different period
      than you left.

UX-16 Excellent, worth preserving: the danger-dialog focus default on Cancel;
      the Enter-key handling that respects which button has focus; the "which
      date order is this?" CSV prompt; the last-admin guard messaging; the
      first-run empty state; and the honesty of the seasonal-hours hint about
      moon sighting.

SECTION 8 - MOBILE / RESPONSIVE FINDINGS
================================================================================

Breakpoints in use: 760px (bottom nav on, tabs off, stats 2-up), 700px (tables
become cards), 480px (form grid 1-up, modal buttons stack), 420px (stats 1-up),
340px (bottom nav type scale).

MOB-1  The sticky clock bar never appears at ANY width (H-6). Above 760px the
       bottom nav is also hidden, so tablet and desktop users have no clock
       control once scrolled.

MOB-2  Mobile tables lose their semantics (H-10). Visually the card layout is
       good; structurally it is a regression.

MOB-3  No landscape handling. manifest.json requests "portrait-primary", but
       that is advisory in a browser. In landscape on a phone (~390px tall) the
       fixed bottom nav plus its raised clock button consumes ~108px of a 390px
       viewport - roughly a quarter of the screen. There is no
       (orientation: landscape) rule anywhere.

MOB-4  The bottom nav at 320px with an admin's six items gives each slot roughly
       43px with 9px labels. It fits, but "Calendar" and "On Time" are at the
       edge of legibility, and 9px text at --muted-2 fails contrast (H-11).

MOB-5  Safe-area handling is partial. The bottom nav correctly pads with
       env(safe-area-inset-bottom), and body/html get 108px of clearance. But
       the toast stack (bottom:18px/12px) and the sticky clock (bottom:14px)
       do not account for the home indicator, so toasts can sit under it on
       notched iPhones.

MOB-6  Native date/time inputs. Extensive, well-documented work has gone into
       this (the 170px floor, the 480px single-column rule, min-height rather
       than fixed height). This looks solid. Not independently re-verified on
       real iOS Safari in this audit - the existing tests/mobile suite covers
       four widths and should be trusted here.

MOB-7  The mobile keyboard is not accounted for. Focusing the note field on a
       phone raises the keyboard over the fixed bottom nav and the form actions.
       No scroll-into-view on focus and no visualViewport handling.

MOB-8  Tapping a bottom-nav item scrolls instantly to #tabContentCard, which is
       good, but the horizontal tab bar is display:none at that width - so on
       mobile there is no way to reach a tab that is not in the bottom nav.
       Today every tab is present, so this is latent rather than active.

MOB-9  Horizontal overflow: none found. Tables are wrapped in overflow-x:auto,
       charts scale by viewBox, filter bars wrap, and long names use
       overflow-wrap:anywhere. This is genuinely well handled.

MOB-10 The 1-second clock interval (M-21) runs while the app is backgrounded on
       mobile, which is the worst place for it.

MOB-11 Bulk operations on mobile are especially exposed to H-8: a 60-second
       sequential import on a phone that may sleep, switch networks, or be
       backgrounded, with no resume and no unload guard.

SECTION 10 - SECURITY FINDINGS
================================================================================

S-1  CREDENTIALS COMMITTED TO A PUBLIC REPOSITORY
     Location: index.html lines 2105 and 2106 hold the Supabase project URL and
     the publishable (anon) key as string literals in a file served publicly via
     GitHub Pages and committed to a public repository. Values are deliberately
     not reproduced in this report.
     Assessment: the anon key is designed to be public - Supabase's model is
     that it carries no authority beyond what RLS permits. So this is NOT in
     itself a vulnerability. It becomes one the moment RLS is wrong, which it
     currently is (C-1): the key plus any employee login is a full compromise.
     It also means the project reference is public, so the auth endpoints are
     directly reachable for credential stuffing.
     Recommendation: keep the key public (that is the design) but (a) fix C-1,
     (b) enable leaked-password protection and consider MFA for admins,
     (c) rotate the key if you ever suspect the SERVICE ROLE key touched this
     repo - confirm it never did, (d) configure Supabase Auth rate limits and
     restrict the allowed redirect URLs, since resetPasswordForEmail is called
     with redirectTo: window.location.href (index.html:5619) and an unrestricted
     redirect allowlist would make that an open-redirect for reset tokens.

S-2  Broken access control - privilege escalation. See C-1. CRITICAL.

S-3  Ineffective security control - registration toggle. See H-3.

S-4  Missing server-side validation. See H-7.

S-5  Cross-site scripting via HTML attribute injection. See M-4.

S-6  Client-side-only enforcement of the last-admin rule. The guard that stops
     the final admin being demoted exists only in the browser
     (index.html:5248-5254). A direct API call bypasses it and permanently locks
     the organisation out of role management, the Admin tab, settings
     administration and user management, with no recovery path short of SQL.
     Note the equivalent rules for deactivation and deletion ARE enforced
     server-side inside the RPCs - so the pattern is understood, it just was not
     applied to role changes. Fix as part of C-1.

S-7  Users can rewrite their own profiles.email. It is a separate column from
     auth.users.email and is granted UPDATE to authenticated. Changing it does
     not affect login, but profiles.email is what admin_list_users, the Team
     tab, the Team & Access list and every audit_log row display. A user can
     therefore impersonate a colleague's identity throughout the admin UI and
     in the audit trail. Fixed by the same column-grant revocation as C-1.

S-8  Session tokens in localStorage. The Supabase default. Any XSS (M-4) yields
     the access and refresh tokens, and the refresh token grants long-lived
     access from anywhere. Mitigate with a CSP (M-23); note that a strict CSP is
     currently impossible because the app loads its only dependency from a
     third-party CDN (C-2) - vendoring it enables script-src 'self'.

S-9  No CSP, no frame-ancestors, no Referrer-Policy. See M-23. The app is
     framable, so an admin can be clickjacked into a destructive action.

S-10 CORS is Supabase-managed and permissive by design (Access-Control-Allow-
     Origin: *) for the REST API. That is correct for their model - authority
     comes from the JWT, not the origin - but it means any origin can drive the
     API with a stolen token.

S-11 Leaked-password protection disabled + 6-character minimum. See M-22.

S-12 Internal SECURITY DEFINER functions exposed as RPCs. See M-24.

S-13 No rate limiting visible on sign-in, registration or password reset beyond
     Supabase defaults. resetPasswordForEmail is callable in a loop from the UI.
     The app correctly returns a generic message for password reset ("If an
     account exists for X...") which avoids enumeration there - but the
     registration path surfaces Supabase's raw error verbatim
     (index.html:5149), which typically distinguishes "already registered".
     That is a user-enumeration oracle.

S-14 Deactivation is not immediate. admin_set_user_active sets banned_until,
     which blocks future token refresh and new sign-ins, but an already-issued
     access token stays valid until it expires (up to an hour). A user
     deactivated for cause retains full access for that window.

S-15 File upload: no true upload surface (imports are read client-side via
     FileReader, never uploaded). Good. But there is no file-size guard, so a
     very large JSON or CSV is read entirely into memory - a self-inflicted
     tab crash rather than a server risk.

S-16 Dependency vulnerabilities: unassessable. There is no package.json, no
     lockfile and no pinned version for the one runtime dependency - it
     floats on supabase-js 2.x from a CDN. This is itself the finding: you
     cannot audit, patch or reproduce your dependency set. See C-2.

S-17 The audit log design is genuinely good and worth protecting: append-only
     by construction (no INSERT/UPDATE/DELETE policy exists; writes happen only
     inside SECURITY DEFINER triggers), admin-read-only, captures old and new
     values, logs before cascade deletes, and records the acting admin rather
     than the affected user. Retain this pattern. Consider adding retention and
     export, since it currently grows unbounded and is only reachable 150 rows
     at a time.

SECTION 11 - PERFORMANCE FINDINGS
================================================================================

P-1  Initial load. One 279KB HTML file (uncompressed; ~55-65KB over gzip),
     plus a blocking cross-origin ESM fetch that itself pulls the supabase-js
     dependency graph. Time to interactive is bounded by a third-party CDN
     round trip you do not control. Vendoring (C-2) removes an entire DNS +
     TLS + fetch chain from the critical path.

P-2  Icons are unoptimised: icon-512.png is 78KB and apple-touch-icon.png is
     22KB for what is a flat two-colour mark. Both would be a few KB as
     optimised PNG or SVG. Only matters at install time.

P-3  Unbounded queries. See H-9 (Team tab downloads every entry), plus the bulk
     pre-check at :5344 and sbFetchEntries with no range. No query in the app
     uses .range() or .limit() except the audit RPC.

P-4  Sequential writes. See H-8. N round trips where 1 would do.

P-5  Full re-render on every mutation. See M-20.

P-6  Always-on 1-second interval. See M-21.

P-7  No pagination or virtualisation in the Log. See M-19.

SCALE PROJECTION (single user unless noted)
   10 entries      Instant. No issues.
   100 entries     Instant. Current real-world scale (345 rows across 8 users).
   1,000 entries   Log with "All Years" builds ~1,000 rows x 11 cells via
                   per-row innerHTML: a visible hitch (~0.3-1s). Charts fine.
                   Team tab now fetches ~1,000 rows to render 8 cards.
   10,000 entries  Log freezes for several seconds and is unusable on mobile.
                   Team tab downloads several MB on every visit and is at real
                   risk of silent truncation by PostgREST's row cap (H-9).
                   Yearly view summarises 10,000 records synchronously on every
                   renderAll(). Print report attempts a 10,000-row table.
   Team of 50 x 3 years (~37,500 rows): the Team tab is not viable at all.

DATABASE
   * Indexing is adequate for current access patterns: entries has
     UNIQUE(user_id, date) which serves both the per-user fetch and the
     ordering. Two audit_log indexes are reported unused.
   * The performance advisor flags 8 RLS policies that re-evaluate auth.uid()
     per row. Wrapping as (select auth.uid()) is a mechanical fix that matters
     once entries grows past a few thousand rows.
   * app_settings.updated_by has no covering index (trivial, 1 row).

SECTION 12 - ARABIC / RTL FINDINGS
================================================================================

STATUS: Arabic and RTL are NOT SUPPORTED. There is no i18n layer, no
translation table, no dir attribute, no [dir="rtl"] CSS rule and no logical
CSS properties anywhere in the file (verified: zero occurrences of dir= or rtl).
The document is hardcoded lang="en".

Given the strong Gulf signals in the product (Sunday-Thursday default week,
Ramadan seasonal hours capped at the statutory 6 hours), Arabic support is a
likely near-term requirement. These are the specific things that will break.

RTL-1  Layout direction. Every layout uses physical properties - margin-left,
       padding-left, border-left, left:, text-align:left/right,
       flex-direction:row. Setting dir="rtl" would mirror text but leave the
       card accent bars, the reminder banner's 4px left border, the
       .period-card::before rail, the punctuality rule's left border, the
       .filter-spacer margin-left:auto and the stat-card top accent all on the
       wrong side. Migrating to margin-inline-start / border-inline-start /
       text-align:start is mechanical and should be done before, not after,
       Arabic strings arrive.

RTL-2  Directional icons. The clock-in arrow points right and clock-out points
       left; the calendar previous/next chevrons point left/right; the sign-out
       icon points right. All five encode "forward" as rightward and must be
       mirrored under RTL.

RTL-3  Mixed Arabic/English text is not isolated. Notes, employee names and
       emails are rendered without dir="auto" or Unicode isolates. An Arabic
       note containing an English word, a number or a time will render with
       punctuation and ordering in the wrong place inside table cells - the
       classic bidi bug. Cheap fix, worth doing NOW even before Arabic UI:
       add dir="auto" to .note-cell, .team-name, .team-email, the note inputs
       and the announcement banner.

RTL-4  Bidi control characters are not stripped (M-5). Under RTL this stops
       being a rendering quirk and becomes a routine source of scrambled
       reports.

RTL-5  CALENDAR SYSTEM MISMATCH - the most serious of these. Dates are
       formatted with toLocaleDateString(undefined, ...), which follows the
       BROWSER locale. On an ar-SA device that yields Hijri dates. So the Log,
       the calendar month label, the reminders and the printed report would
       display Hijri, while <input type="date">, the stored value and every
       comparison remain Gregorian ISO. A user would see a date in the table
       that does not match the date they typed. Any Arabic rollout must pick a
       calendar explicitly (e.g. 'en-GB'/'ar-SA-u-ca-gregory') rather than
       inheriting the locale.

RTL-6  Digits. Number.toLocaleString() in the admin stats produces Arabic-Indic
       digits on Arabic locales, while minutesToHoursStr() emits raw Latin
       digits with "h"/"m" suffixes. The same screen would mix two numeral
       systems.

RTL-7  Hardcoded English strings. formatTime12 emits "AM"/"PM" literally.
       DAY_NAMES and DAY_FULL are English arrays. TYPE_LABELS, AUDIT_LABELS and
       every toast, modal, hint, empty state and error message are English
       literals inline in the code - roughly 200 strings with no extraction
       point. This is the bulk of the i18n work and is architectural: it needs a
       string table before anything else can proceed.

RTL-8  Charts. renderBarChart positions labels left-to-right with
       text-anchor:end for rotated labels. Under RTL the bar order and the
       label anchors both need to flip.

RTL-9  Long Arabic text. Arabic strings typically run 20-30% longer than
       English. The bottom-nav labels (already ellipsised at 9-10px), the stat
       card labels and the seal are the places that will overflow first.

RTL-10 The layoutBottomNav() left/right slot algorithm is direction-agnostic in
       its maths, but "left" and "right" would need to swap meaning so the tab
       order matches reading order.

SECTION 14 - FAILURE & RECOVERY FINDINGS
================================================================================

F-1  CDN unavailable            -> Total silent failure, no message. C-2. CRITICAL.
F-2  Offline (installed PWA)    -> Same as F-1. The shell loads, the app does not.
F-3  Offline (already loaded)   -> Each action fails with a toast carrying the raw
                                   fetch error. No offline indicator, no queue, no
                                   retry. A punch made offline is simply lost.
                                   There is no navigator.onLine handling anywhere.
F-4  Request times out          -> No timeout is set on any call. The button stays
                                   in "Saving..." indefinitely; the user cannot
                                   cancel and will likely force-reload, which for a
                                   bulk operation leaves partial state (H-8).
F-5  Server returns an error    -> Surfaced as a toast with the raw message (UX-8).
                                   Non-destructive and honest, but unhelpful.
F-6  Server returns bad data    -> Not defended. rowToEntry trusts every field.
                                   A malformed clock_in propagates into every
                                   aggregate (H-7).
F-7  Auth fails / expires       -> onAuthStateChange fires with no session and the
                                   app returns to sign-in. Correct behaviour - but
                                   any unsaved form input is lost with no warning,
                                   and mid-bulk-operation this abandons the run.
F-8  Authorisation fails        -> RLS denial surfaces as a raw PostgREST string.
                                   For a non-admin who somehow reaches a settings
                                   save this reads as a bug rather than a
                                   permission boundary.
F-9  Refresh during submit      -> No beforeunload guard. Partial writes for bulk
                                   operations; a single entry is atomic so that
                                   case is safe.
F-10 Page closed mid-operation  -> Same. Silent partial completion.
F-11 Two tabs open              -> Both hold independent in-memory `entries`
                                   arrays with no cross-tab sync (no storage
                                   event listener, no realtime subscription).
                                   Tab A deletes an entry; tab B still shows it,
                                   and editing it there produces a confusing
                                   failure. Signing out in tab A does correctly
                                   sign out tab B (Supabase broadcasts it), which
                                   then discards tab B's unsaved work silently.
F-12 Two admins act at once     -> Last write wins with no conflict detection.
                                   updated_at exists on entries but is never
                                   compared. Admin A and admin B editing the same
                                   employee's day silently overwrite each other.
F-13 Network reconnects         -> No recovery, no refetch, no "reconnected"
                                   signal. The user must reload manually.

The consistent theme: failures are non-destructive and honest at the single-entry
level (good), but the app has no concept of connectivity, no retry, no timeout,
no cross-tab awareness and no protection for multi-step operations.

SECTION 15 - EDGE CASES EXAMINED

TESTED / REASONED - HANDLED CORRECTLY
  * Duplicate date on insert: UNIQUE(user_id,date) enforced in the DB, 23505
    mapped to a clear message, and the client offers "Replace it?" first. Good.
  * CSV quoting: quoted fields, escaped double-quotes, embedded newlines, CRLF
    and the Excel BOM are all handled. Genuinely thorough.
  * Ambiguous D/M vs M/D dates: detected, resolved once via a dialog rather than
    guessed per row. Exemplary.
  * Excel day-fraction times ("0.354"), compact times ("0800", "800"), bare
    hours ("16"), period separators ("8.00 AM"): all parsed.
  * Leap years: daysInMonth uses new Date(y, mo, 0), which is correct.
  * DST transitions: date iteration uses setDate(), which is DST-safe. No
    infinite loops possible.
  * Month/year rollover in the calendar: setMonth() handles Dec->Jan correctly.
  * Empty settings / missing settings row: normalizeSettings falls back
    defensively and clamps every numeric field to a sane range.
  * Legacy backup formats: v1 (bare array), v2 ({entries}) and v3 ({entries,
    settings}) all import; the decimal targetHours -> targetMin migration is
    correct and the comment explaining why it checks `raw` not `out` is right.
  * Runaway loops: every date scan is capped (400 iterations) AND correctly
    distinguishes "hit the cap" from "reached the end", refusing to proceed on
    an undercount rather than silently applying to fewer days. Well done.
  * Bulk caps: 62 workdays for a range, 500 entries for apply-to-everyone.
  * Self-lockout: cannot delete your own account, cannot deactivate yourself,
    cannot delete or deactivate the last admin - all enforced SERVER-SIDE in the
    RPCs. (Role demotion is the exception - see S-6.)
  * Zero / negative / decimal settings values: validated and clamped on save.
  * Empty working-days selection: rejected with a clear message.
  * Overlapping seasonal periods: rejected on save (but not on import - L-9).

EDGE CASES NOT HANDLED
  E-1   Clock out before clock in -> silent 16h shift (H-5).
  E-2   Clock in == clock out -> 0h worked, counts as a logged day, drags the
        average down with no warning.
  E-3   A Regular day with no times -> inflates Target, contributes no Diff (C-4).
  E-4   Leave on a non-working day -> charged against entitlement (H-14).
  E-5   A date far in the future or the distant past -> accepted; permanently
        pollutes the Year filter and the year-over-year chart (H-7).
  E-6   type set to an unknown string -> "undefined" rendered in the Log,
        Calendar tooltip, print report and audit detail (H-7).
  E-7   A 10MB note -> accepted, then loaded on every page view (H-7, L-16).
  E-8   Working days changed retroactively -> every historical day is
        recalculated. The hint does say "Changes apply to all calculations,
        including past entries", which is honest, but a year of history silently
        re-scoring is a large consequence for a checkbox.
  E-9   Seasonal target vs seasonal start/end mismatch -> not validated
        (a 6h target with 08:00-16:00 hours is accepted).
  E-10  Annual leave entitlement changed mid-year -> balance retroactively
        recomputed; no pro-rating for joiners, no carry-over.
  E-11  A deactivated user still appears in the viewer switcher, the Team tab
        and "Apply to Everyone" totals, with no visual distinction (only the
        Admin tab marks them).
  E-12  A user with zero entries in the Team tab -> renders as 0 / 0h / "—",

  E-13  Exactly one team member -> "Apply to everyone" still offers to

  E-14  A week spanning a month boundary -> weekly cards are grouped by week key
        so they correctly span months, but the month filter will show a partial

  E-15  Two entries for the same date across different users in bulk apply ->
        handled correctly via the userId|date map.
  E-16  Timezone travel: an employee flying across zones has punches recorded
        against the device's local date, so a day can be duplicated or skipped
        entirely at the boundary. Not handled and not detectable.

SECTION 16 - BUSINESS LOGIC ISSUES
================================================================================

B-1  Aggregates do not reconcile; missed days invisible; WFH excluded. C-4.
B-2  Reversed times become a silent overnight shift. H-5.
B-3  Streak resets every morning. H-13.
B-4  Leave charged for non-working days. H-14.
B-5  Half-day target reaches the row but never the aggregate. C-4(d).

B-6  Lateness is provisional but presented as final.
     CONFIRMED. With lateOnlyIfShort on (the default), a day that is still open
     is treated as forgiven: arriving 11:30 against an 08:00 start measures
     lateMin = 0 while clocked in, and lateMin = 210 once clocked out 3.5h
     short. So the On Time tab reports a spotless record all day and flips
     retroactively at clock-out. A manager checking at 2pm sees the wrong
     answer, and there is nothing marking the figure as provisional.
     Location: index.html:2450 (the `forgiven` calculation)
     Fix: show pending days separately - "3 days still in progress, not yet
     assessed" - rather than counting them as on time.

B-7  Week start is hardcoded to Sunday.
     weekStartDate() always uses d.getDay(), independent of settings.workDays.
     Correct for the Sun-Thu default; wrong for a Mon-Fri organisation, where
     every weekly card straddles two working weeks and the "vs. last week"
     trend compares mismatched periods.
     Location: index.html:2478-2482
     Fix: derive the week start from the first configured working day, or make
     it an explicit setting.

B-8  Target hours and standard start/end can contradict each other.
     Nothing validates that standardOut - standardIn is consistent with
     targetMin. Set 08:00-16:00 with a 7h target and the app simultaneously
     reports "met target" and "left early". See UX-3.

B-9  Grace period applies to arrival and departure identically.
     A single graceMin governs both. Most policies treat a late arrival and an
     early departure differently. Minor, but it is a policy assumption baked in
     with no way to express the alternative.

B-10 The overtime bank never carries over and never resets explicitly.
     It is recomputed from the current calendar month every time. There is no
     accrual, no cap, no payout and no carry-forward - which is fine as a
     display, but the name "Bank" implies a balance that persists.

B-11 Excused day types are hardcoded.
     EXCUSED_TYPES = leave, sick, holiday. Business Trip and Training are NOT
     excused, so a full week of training shows as a full week of missed target.
     Combined with C-4 (training is also excluded from the average), a training
     week is doubly misrepresented: it neither counts as worked nor is forgiven.
     Location: index.html:2123
     Fix: make excused/counts-as-worked configurable per type.

B-12 No approval workflow. Any user can enter any leave, any hours, any day,
     retroactively, with no manager approval step and no locked periods. Once a
     month is signed off, nothing prevents it being edited afterwards - and the
     print report carries a signature line implying it was. Consider a period
     lock.

B-13 No tenancy boundary. Every admin sees every user in the database. There is
     no organisation, department or manager scope anywhere in the schema. Fine
     for one company; blocking for anything else.

SECTION 17 - ARCHITECTURE / CODE ISSUES
================================================================================

A-1  A 5,907-line single file.
     1,173 lines of CSS, ~900 of markup and ~3,800 of JavaScript in one file,
     against a project convention (CLAUDE.md) of keeping files under 500 lines.
     Everything works, but: no module boundaries, no way to test a unit without
     the string-extraction harness in tests/, merge conflicts on every change,
     and no tree-shaking. The single-file constraint was clearly deliberate
     (zero-build deployment to GitHub Pages) and that has real value - but it
     has been outgrown. A minimal build step (esbuild, ~10 lines of config)
     would preserve single-file OUTPUT while allowing sane source structure,
     and would also solve the vendoring problem in C-2.

A-2  Business logic and DOM manipulation are fused.
     computeEntry() and summarize() are pure and testable - good. But
     renderStats(), renderLog() and renderPunctuality() interleave calculation,
     formatting and getElementById calls, so the display rules cannot be tested
     without a browser. The extraction harness in tests/ is a clever workaround
     for a structural problem rather than a solution to it.

A-3  THE SCHEMA IS NOT IN VERSION CONTROL.
     supabase-schema.sql is referenced in the app's own error text
     (index.html:1206) but is not committed. The tables, the 11 RLS policies,
     the 10 functions and the 5 triggers - the entire authorisation model, the
     thing that C-1 shows is load-bearing - exist only in the live project.
     There is no migration history, no review trail and no way to recreate the
     backend. This is the single largest architectural risk after C-1, because
     it means security-critical configuration is changed by hand with no
     review and no rollback.
     Fix: adopt supabase/migrations, commit the current schema as the baseline,
     and require every future change to go through a migration file.

A-4  Duplicated business logic.
     The hours calculation exists twice: computeEntry() (index.html:2421) and
     again inline in renderTeam() (:5453-5462), where the "only Regular counts"
     rule and the overnight wrap are re-implemented. Any fix to C-4 must be
     applied in both places or the Team tab will disagree with every other
     screen. Similarly, the date-range scan loop is written three times
     (:4181-4196, :5300-5316) with subtly different rules.

A-5  Magic numbers and hardcoded values.
     400 (scan cap, twice), 62 (max workdays per range), 500 (bulk cap),
     150 (audit log limit), 14 (backup reminder days), 360 (Ramadan minutes),
     700 (profile retry delay), 21 (default leave days), 5 (backup threshold).
     Most have an explaining comment - which is better than most codebases -
     but none is configurable and several encode policy, not implementation.

A-6  RAMADAN_DATES is a hardcoded five-year table (2027-2031).
     After 2031 the "+ Ramadan" button silently stops offering anything and
     shows an informational toast. This is a documented, dated cliff sitting
     in the code with no reminder attached.  index.html:2828-2834

A-7  Inconsistent visibility patterns.
     Three different mechanisms for showing and hiding the same kind of element:
     .show classes (reminder banners), inline style.display (empty states,
     filter bars, tabs), and .open classes (cards, accordions). H-1 is a direct
     consequence of two of them colliding on one element. Standardise.

A-8  Error handling is inconsistent.
     Some paths toast, some write to qcStatusNote, some console.error and
     swallow (loadAppSettings, index.html:5750), some set inline auth messages.
     There is no central error handler and no distinction between "the user did
     something invalid" and "the backend failed".

A-9  No state management.
     `entries`, `settings`, `viewedUserId`, `isAdmin`, `isOwnData`, `editingId`,
     `selectModeActive` and `calendarViewDate` are module-level mutable
     variables. Every render reads them directly. This is workable at this size
     but is why H-2 (a background token refresh silently changing viewedUserId)
     is possible at all - there is no single place that owns "whose data are we
     looking at" and no way to observe it changing.

A-10 No build, no linting, no CI.
     No package.json at the root, no eslint, no formatter, no CI workflow. The
     test suite in tests/ is good and must be run by hand.

A-11 Dead code. The sticky clock bar and its observer (H-6). Also
     app_settings.default_settings is defined in the schema and never read.

A-12 Positive: the comments are exceptional.
     Nearly every non-obvious decision carries a comment explaining the failure
     it was written to prevent - the position:fixed on the head menu escaping
     overflow:hidden, the min-height rather than fixed height on native
     date/time controls, the punchInFlight flag surviving the re-enable in
     updateViewingBanner, the CanvasText/Canvas system colours on the viewer
     dropdown options, the Enter-key handling in danger dialogs. This is a real
     asset and should survive any refactor.

SECTION 18 - POTENTIAL RISKS (NOT REPRODUCED)
================================================================================

Listed separately because these are reasoned from the code and not executed
end to end. Each should be verified before being scheduled.

PR-1  onAuthStateChange deadlock. Supabase explicitly documents that calling
      other supabase methods inside the callback can deadlock, because the
      callback holds the auth lock. handleSignedIn is async and immediately
      awaits a profiles query (index.html:5805). Would present as an
      intermittent hang on sign-in. Fix defensively regardless (see H-2).

PR-2  PostgREST row-cap truncation on the Team tab. Depends on the project's

TOP 10 THINGS TO FIX FIRST
================================================================================

 1. C-1  PRIVILEGE ESCALATION - any user can make themselves an admin.
         Proven against the live database. Every other access control in the
         product is downstream of this one, so until it is fixed nothing else
         you enforce is actually enforced - and the fix is three SQL
         statements. Also audit existing role_change rows for prior abuse.
         Nothing else on this list matters as much, and nothing else is
         cheaper.

 2. C-2  THE APP DIES SILENTLY WHEN ONE CDN IS UNREACHABLE.
         Complete loss of availability from a dependency you do not control,
         presented to the user as a working screen that ignores them. It also
         hits every installed PWA opened offline - the most likely real-world
         path. Vendoring the file fixes the outage, the proxy case, the offline
         case AND the unpinned supply-chain exposure in one change, and unblocks
         a real CSP.

 3. C-4  THE HEADLINE NUMBERS DO NOT RECONCILE.
         Total 16h, Target 32h, Overtime 0h on the same card. A missed workday
         moves the overtime bank by zero. Three 9-hour WFH days average to "0h".
         This is a timesheet product; these figures are printed onto a document
         people sign. Wrong-but-plausible numbers are more damaging than a
         crash because nobody catches them. Fix third only because 1 and 2 are
         cheaper and broader.

 4. C-3  "APPLY TO EVERYONE" DESTROYS REAL CLOCK DATA IRREVERSIBLY.
         One admin click can blank recorded hours for the whole team across a
         date range, with no undo and no preview of what will be lost. The data
         is recoverable only by hand through the audit log. Make it skip
         occupied days by default - a contained change to one handler.

 5. H-1  THE "EDITING SOMEONE ELSE'S RECORD" WARNING HAS NEVER RENDERED.
         The safeguard was written, reviewed and shipped, and an inline style
         has silently suppressed it since. An admin can corrupt a real
         employee's attendance believing it is their own. The fix is deleting
         one attribute, which makes the cost/benefit unbeatable - and it pairs
         directly with C-3 and H-2.

 6. H-3  THE REGISTRATION LOCK DOES NOTHING.
         An admin who has closed signups has not closed signups. On its own
         that is bad; combined with C-1 it means anyone on the internet can
         create an account and then promote themselves to administrator of your
         HR system. These two findings must be fixed together or not at all.

 7. H-11 + H-10  ACCESSIBILITY FALLS BELOW THE LEGAL FLOOR.
         Contrast measured at 2.06:1 where 4.5:1 is required, across a dozen
         classes in both themes; and on mobile every data table loses its
         semantics entirely, making the primary interface unusable with a
         screen reader. For an HR tool this is compliance exposure, not polish.
         The contrast half is two token edits.

 8. H-4  EMPLOYEES CANNOT SET THEIR OWN SCHEDULE AND ARE NEVER TOLD.
         Every new user silently gets Sunday-Thursday 08:00-16:00. In a
         Monday-Friday organisation every number they see is wrong, every
         Friday shows red, and their punctuality record looks terrible. There
         is no gear icon and no message. This is the difference between users
         trusting the app and abandoning it in week one.

 9. H-2  TOKEN REFRESH SILENTLY RESETS STATE AND DISCARDS INPUT.
         Once an hour the app cold-boots: unsaved form input is wiped and an
         admin is yanked out of the employee record they were editing without
         being told. With H-1 unfixed there is no banner to catch it, so the
         next save lands on the wrong person. Three lines of event filtering.

10. H-7 + H-8  NO SERVER-SIDE VALIDATION, AND BULK WRITES ARE UNSAFE.
         The database accepts "99:99" as a clock time and arbitrary strings as
         a day type, so the UI's careful validation is advisory only. Meanwhile
         imports and bulk actions run one request at a time for up to a minute
         with no cancel, no batching and no unload guard, so partial completion
         is routine and invisible. A single migration plus a single batched
         upsert closes both.

APPLICATION FROM "SHOULD NOT BE ROLLED OUT FURTHER" TO "DEPLOYABLE WITH KNOWN,
DOCUMENTED GAPS".
